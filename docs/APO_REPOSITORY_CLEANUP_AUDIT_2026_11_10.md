# APO repository cleanup and conflict audit
**Audited:** 10 November 2026 (Asia/Manila)  
**Repository:** `andreivonmariano-dotcom/Wildlife-survey-app`  
**Status:** Verified structural/documentation cleanup; Android source cleanup and branch integration pending. This report does not claim a signed APK or complete codebase migration.

## Core findings

1. **Default and development branches have separate histories.** `main` contains the historical Android v0.15 implementation and the approved APO charter Markdown v1.2. Its inspected tree contains **80 files** and 2 workflows. `feature/apo-rc111-unified-field-first-ui-v171` contains **789 files** and **69 workflows**, and is **3,790 commits ahead and 227 behind** `main` in the GitHub comparison. A blanket merge or copy from `main` is unsafe. README and source-directory counts refer to the inspected commits only.
2. **RC111 branch split.** The RC111 UI-overhaul HEAD `9815f0554f345706baa52e02842e322f1306e563` and unified-field-first HEAD `f7df249d2ea124591d6fbf343b9a5a9f7c594eb8` diverged. Comparison found 25 differing tracked paths. Both declare versionCode 171. There is no confirmed owner-approved selection between them. Do not choose a lineage, merge their APK sources, or treat either source branch as a signed release without separate verification.
3. **The approved charter is missing from the inspected RC111 tree.** `docs/APO_OFFLINE_FIRST_PRODUCT_CHARTER_v1.0.md` (document content v1.2) exists on `main`, not the inspected RC111 branch. The canonical owner-approved Google Doc remains https://docs.google.com/document/d/1khryohmOO5QsOmuKchv8VWWu7Qxcq7zxVDZX9L3qCJA/edit. Propagate the exact approved charter and compatible high-priority instructions only after choosing a development lineage; any substantive charter edit first requires explicit owner approval.
4. **Internal legacy names remain extensive.** In the RC111 field-first tree, **141 tracked paths contain `likas` case-insensitively**, including 9 Java classes named `Likas*`, graphics, forest assets, policy and QA filenames, a source-catalog JSON, tests, and a CI workflow. Example live class: `LikasSettingsActivity`. Example persisted preference key: `likas_ui`. The inspected Android manifest already declares the visible application label `Apo`. Rename public-facing labels and new outputs to APO. Keep package `org.phwildlife.survey.beta08` and persistent/internal identifiers until reference mapping, migration and release tests have passed.
5. **Obsolete RC4 safety gate.** `.github/workflows/likas-pr-lineage.yml` invokes `scripts/check_pr_against_rc4.py`. The latter explicitly looks for `brand.setText("LIKAS")`, the SQLite v27 constructor and RC4 startup/forest sprite conditions. These checks are inconsistent with the newer APO manifest, schema 29 and RC111 app lineage. The gate is inappropriate as the only current-branch release/merge safety proof. Retire or replace it only alongside tested RC111 lineage, migration, signing, evidence and asset-integrity checks.
6. **Stale CI and historical draft volume.** RC111 contains 69 workflows, most named for historical RC and screen-specific QA stages. GitHub's open-PR collection returned at least 100 open PRs; the first 100 included numerous old LIKAS-titled drafts and did not contain a submitted RC111 PR. Older workflows can increase maintenance/review surface; the actual running-job cost requires checking their event and branch filters. Do not delete tests, reviews or signed-build evidence until its successor path is verified. Move historical design/QA guidance out of the active instruction surface, leaving traceable links.
7. **Contradictory scientific/editorial guidance.** `docs/LIKAS_PUBLICATION_FIRST_CONTENT_STANDARD.md` appears in RC111 and still presents publication-first work as an editorial policy. APO Charter v1.2 governs educational, direct, concise offline species and habitat information. Primary literature provenance and scientific uncertainty remain required; publication-style page structures and defensive copy are obsolete. Mark the older policy explicitly superseded in the selected Android branch. Keep its source records and evidence for traceability.
8. **Misleading end-user reference-import action.** RC111 field-first `LikasSettingsActivity.java` visibly labels a control `Import source files` / `Add supported reference inputs`, and links to `ImportActivity`. The inspected `ImportActivity` is a legacy v0.7 survey backup ZIP importer. Clarify the UI as an optional **legacy survey backup restoration** tool, and remove reference-import wording; preserve local survey backup/restore compatibility. Check all routes for unintended reference-import prompts before a build.
9. **Multiple generations of book data and assets.** The RC111 assets include `phlibrary_book01_v175_01` through `08`, `phlibrary_book01_v182.json.gz.b64`, habitat/editorial overlays, `paic714_master.csv`, image manifests and other evidence bundles. These may be runtime dependencies, source history, or historical fallbacks; classification requires a code-reference inventory and tests before removal. Do not deduplicate scientific records by comparing filenames alone. Verify 714/715 edition and taxon identifier crosswalks rather than silently combining lists.
10. **Public-repository review of private-named material.** The RC111 branch contains `app/src/main/assets/likas_ph_checklists_v2026_private.b64` in a public GitHub repository. The filename alone does not establish its permissions or origin. Verify its rights, whether it contains private or redistributable material, current consumers, and whether inclusion complies with owner permission and source licensing before release. Do not assume base64 encoding protects confidential data.

Remove unused duplications only with proven equivalent data and passing regressions. Retain source provenance and previous research versions as archive.

Close/archive them in documented batches when their code and evidence are safely represented. Avoid deleting remote history or orphaning signed-artifact provenance.

**Exit criteria:** Canonical APO branch selected; current charter accessible on that branch; no active contradictory development instructions; automated branding/editorial checks; controlled CI; source-preserving data cleanup; signed build and data-preserving upgrade QA; owner-reviewed results. Until these gates pass, cleanup is **documentation and release-hygiene only**.
