# Proposed APO-31 | Controlled continuity recovery after signing-key loss
27 November 2026 (Asia/Manila) — PROPOSAL ONLY. Canonical Charter v1.3 remains unchanged.

## Exact proposed addition
**APO-31 | Controlled continuity recovery after signing-key loss.** When recovery of the existing signing key has been exhausted and the product owner explicitly approves this exception, a separately installed successor may use a new owner-approved Android application ID and a new protected signing identity. Keep the original installation and verified recovery archives intact. Require a complete, validated transfer of user-created records, metadata, media and local settings into an empty successor workspace. Verify synthetic and authorized migration fixtures, rollback, offline operation, restored record identity and media integrity, and physical-device acceptance before successor deployment or migration completion. No automatic uninstall or deletion of original records is allowed. The new signing identity must have documented secure custody and independently recoverable encrypted backups before distribution. The owner must approve the final package ID, signer adoption and retirement of the legacy app separately. Preserve historical source, identifiers, data provenance, reference integrity and release evidence. This exception does not permit destructive reinstalls, undocumented signer changes, or relaxed scientific or release gates.

## Affected requirements and justification
Narrow exception to APO-08 and APO-20 only, subject to APO-13–15 approval. APO-21, APO-25, APO-29, scientific and offline requirements remain binding. Original package org.phwildlife.survey.beta08 and original signer continue to be protected. Proposed successor ID org.phwildlife.survey.apo is not approved, reserved, or implemented. Original key missing in searched GitHub caches/secrets, laptop folders and project ZIP contents, four committed tree snapshots, and default-branch history for four likely paths. Further owner-held offline backups may still exist. A parallel installation reduces risk by preserving the original throughout backup/restore. No automatic uninstall.

## Evidence and migration acceptance
FieldBackupArchive v1 accepts schema27–29, requires no active survey for export, and permits restore only into an empty workspace. Archive includes SQLite, flat record_media and acoustic files, shared prefs and hash manifest. Limits: 256 MiB per file, 768 MiB total, 8000 entries, safe paths. Export requires SQLite >=3.27 VACUUM INTO. Current implementation does not establish semantic completeness for every attachment or guarantee process-death recovery; test representative supported histories, full record/media linkage, failure injection and physical-device restore. Read-only backup preflight scripts/verify_apo_backup.py and scripts/test_verify_apo_backup.py committed in candidate branch; all ten synthetic tests passed locally. Verifier is not actual Android import.

Create two private copies of an exported recovery ZIP outside the app. Compare aggregate counts and actual records locally; do not upload real sensitive location archives to CI. Test a new signed package side by side, using synthetic data first, and independently test subsequent in-place upgrade under the new signer. Keep original app and backups after owner acceptance unless separate retirement approval. Use secure key custody, protected CI secrets and independently recoverable encrypted backups; no cache-only key retention.

Private synthetic rehearsal workflow run 45993005639: uses byte-exact RC116 code176 and ephemeral QA-only different signing certificate on two fresh emulators. No production key or user data. It tests same-package cross-signer archive portability in isolated environments, not new-package deployment. At the time of this proposal the native result was pending. No new APK delivered.
